# Chanel AI Investment Portfolio

A static, GitHub-Pages-ready microsite presenting the eaef-multiprocedure-eater
AI-automation portfolio analysis for Chanel across four process domains:

- **FP&A** — Financial Planning & Analysis (`domains/fpa.html`)
- **O2C** — Order-to-Cash (`domains/o2c.html`)
- **R2R** — Record-to-Report (`domains/r2r.html`)
- **S2P** — Source-to-Pay (`domains/s2p.html`)

`index.html` is the combined landing page (rollup KPIs across all four domains
plus links into each dashboard). `styleguide.html` documents the design
tokens.

## Live structure

```
index.html              combined portfolio landing page
styleguide.html          design-token reference / reuse guide
styles/
  dashboard.css          shared component + token stylesheet (all pages)
  landing.css            landing-page-only components (domain cards, share bar)
domains/
  fpa.html  o2c.html  r2r.html  s2p.html      per-domain 9-section dashboards
brands/
  chanel.json            Chanel's brand token config
scripts/
  apply_brand.py         re-skinning engine (brand config -> branded HTML)
```

## Why this is reusable for the next client

The eaef-multiprocedure-eater pipeline already outputs fully-baked,
self-contained dashboard HTML per client/domain — correct data, correct
structure, but styled in a generic dark IBM-Carbon theme. Rather than
hand-editing that output per client, this repo separates three concerns:

1. **Structure + data** — untouched, exactly as generated by the pipeline.
2. **Brand** — a small JSON config (`brands/<client>.json`) naming that
   client's palette and fonts.
3. **The re-skin step** — `scripts/apply_brand.py` mechanically swaps every
   color/font literal in the generated HTML for the brand config's values,
   with no hand-editing of HTML/CSS/JS.

### To onboard a new client

1. Get that client's raw eaef-multiprocedure-eater dashboard exports (one
   HTML per domain, plus each domain's `portfolio_synthesis.json`).
2. Copy `brands/chanel.json` to `brands/<client>.json` and replace the hex
   values with the new brand's palette — see the comments in that file and
   the walkthrough on `styleguide.html` for what each token controls, and
   which three (GO/CONDITIONAL/NO-GO status colors) should **not** be
   reassigned.
3. Run:
   ```
   python3 scripts/apply_brand.py --brand brands/<client>.json \
     --in-dir <raw_exports_dir> --out-dir domains/
   ```
4. Re-extract the shared `<style>` block from one branded file into
   `styles/dashboard.css` (the apply_brand step re-skins the block wherever
   it lives, inline or linked) — or simply re-run the same extraction used
   to build this repo (see git history / `scripts/apply_brand.py` docstring).
5. Rebuild `index.html`'s combined KPI numbers from the new client's four
   `portfolio_synthesis.json` files (`total_annual_savings`, `go_uc_count`,
   `conditional_uc_count`, `fte_reduction_estimate`, `consolidated_impl_cost`,
   `per_sop_impl_cost_total` — sum across domains).
6. Push to a new GitHub repo and enable Pages (see below). No HTML, CSS
   class name, or JavaScript function needs to change.

## Hosting on GitHub Pages

1. Create a new **public** GitHub repository (GitHub Pages' free tier only
   serves public repos; private Pages requires GitHub Pro/Team).
2. Push this folder's contents to that repository's default branch.
3. In the repo's **Settings → Pages**, set "Source" to "Deploy from a
   branch", branch `main`, folder `/ (root)`. Save.
4. GitHub will publish the site at
   `https://<your-username>.github.io/<repo-name>/` within a minute or two.
   That URL serves `index.html` — share that link.
